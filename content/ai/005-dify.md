## 一、什么时候用工作流？（而不是简单聊天）

普通聊天助手是"一问一答"，工作流是"多步骤处理"。以下场景应该用工作流：

✅ 适合用工作流的场景

- **需要判断/分支**：根据用户意图走不同流程（如售后 vs 销售咨询）
- **需要调用外部工具**：查数据库、调 API、发邮件等
- **需要多步骤处理**：如"接收需求 → 生成草稿 → 审核 → 发布"
- **需要结构化输出**：固定格式的报告、表格、JSON 等
- **需要可解释/可调试**：每个步骤都可见，方便排查问题

⚠️ 继续用简单聊天的场景

- 纯知识问答（直接用知识库 + 聊天助手就够了）
- 开放式闲聊
- 简单的文本生成任务

## 二、工作流核心节点（必知）

Dify 工作流画布上有这些基础节点，理解它们是编排工作流的基础：

**START**

#### 开始节点

工作流的入口，定义输入变量（如用户输入、文件等）

**LLM**

#### LLM 节点

调用大模型推理，填写提示词，配置模型

**IF/ELSE**

#### 条件分支

根据条件判断，走不同分支路径

**TOOL**

#### 工具节点

调用外部工具（搜索、API、代码执行等）

**TEMPLATE**

#### 模板节点

用 Jinja2 语法拼接变量，生成格式化文本

**END**

#### 结束节点

工作流的出口，定义输出格式

**LOOP**

#### 循环节点

对数组中的每个元素执行相同操作

**CODE**

#### 代码节点

执行 Python / JavaScript 代码，做数据处理

## 三、实战：搭建第一个工作流

跟着步骤走，搭建一个**"智能客服路由工作流"**——根据用户输入自动判断意图，走不同处理分支。

📐 工作流目标

用户输入问题 → AI 判断意图（售后 / 产品咨询 / 其他）→ 调用对应知识库回答 → 输出结果

开始接收用户输入

⬇️

LLM 节点判断用户意图（输出：after-sale / product / other）

⬇️

条件分支if 意图 == after-sale → 分支A；elif 产品咨询 → 分支B；else → 分支C

⬇️（分支A 示例）

LLM 节点结合"售后知识库"生成回答

⬇️

### Step 1：创建工作流应用

**1** 

#### 新建工作流应用

Dify 控制台 → 工作室 → 创建应用 → 选择**"工作流"** → 填写应用名称（如"智能客服路由"）

**2** 

#### 认识画布界面

- **左侧面板**：节点库，拖拽添加节点
- **中间画布**：拖拽节点、连线，构建流程
- **右侧面板**：选中节点后，在这里配置节点参数
- **右上角**：预览、发布、运行日志

### Step 2：添加"意图识别"LLM 节点

**3** 

#### 配置开始节点

点击"开始"节点 → 右侧 → 添加变量：

- 变量名：`user_query`，类型：文本，必填

**4** 

#### 添加 LLM 节点做意图识别

- 左侧拖一个"LLM"节点到画布
- 从"开始"节点拉线连接到这个 LLM 节点
- 选中 LLM 节点，右侧配置：
  - 模型：选择你配置的模型（如 DeepSeek-V3）
  - 提示词：见下方示例
  - 输出变量名：`intent`

\# 意图识别提示词（填入 LLM 节点）

请判断以下用户问题的意图，只输出以下三者之一：

\- after-sale（涉及退货、换货、维修、售后问题）
\- product（涉及产品功能、规格、价格咨询）
\- other（其他问题）

用户问题：
{{ user_query }}

### Step 3：添加条件分支

**5** 

#### 添加条件节点

- 左侧拖一个"条件分支"节点到画布
- 从意图识别 LLM 节点拉线连接到条件节点
- 选中条件节点，右侧配置：
  - 条件 1：`intent` == `after-sale` → 分支 A
  - 条件 2：`intent` == `product` → 分支 B
  - 否则 → 分支 C（默认）

### Step 4：为每个分支添加回答节点

**6** 

#### 分支 A（售后）：添加 LLM 节点

- 拖一个 LLM 节点，从条件节点的"分支 A"连线过来
- 提示词：结合售后知识库，回答用户问题
- 如果有售后知识库，在"上下文"里关联它

**7** 

#### 分支 B / C：同理添加 LLM 节点

分支 B 用产品知识库，分支 C 用一个通用提示词回复"已记录，人工会联系您"

### Step 5：添加结束节点并测试

**8** 

#### 连接结束节点

把三个分支的 LLM 节点都连到同一个"结束"节点。结束节点输出变量设为各分支 LLM 的输出。

**9** 

#### 预览测试

点击右上角"预览"，输入测试问题：

- "我买的耳机坏了能换吗？" → 应该走分支 A（售后）
- "XX 产品有什么功能？" → 应该走分支 B（产品咨询）
- "今天天气怎么样？" → 应该走分支 C（其他）

## 四、调试工作流技巧

🔧 调试工具

- **运行日志**：每次运行后点击"查看日志"，可以看到每个节点的输入输出
- **单步调试**：在画布上右键节点 → "从此节点开始运行"，只跑部分流程
- **变量检查**：在 LLM 节点提示词里临时加一句"请输出你收到的变量：{{ user_query }}"，验证变量传递是否正确
- **节点颜色**：运行后绿色=成功，红色=失败，灰色=未执行

## 五、工作流最佳实践

✅ 设计原则

- **先画流程图再拖节点**：在纸上画出完整流程，再进 Dify 实现
- **每个节点做一件事**：不要把多个逻辑塞进一个 LLM 节点
- **给变量起好名字**：`intent` 比 `result` 好懂 10 倍
- **设置默认分支**：条件分支一定要有"否则"兜底，避免流程中断
- **控制流程长度**：超过 15 个节点建议拆成两个工作流，通过 API 串联

## 六、进阶话题

掌握了基础工作流后，下面是几个能让你的工作流从"能用"升级到"好用"的进阶技巧。

### 6.1 循环节点（Iterator）实战：批量处理

循环节点用于遍历一个列表，对每个元素执行相同的操作。最常见的场景：**批量处理客户消息**或**遍历知识库召回的多条结果**。

🔄 循环节点使用场景

- **批量翻译**：遍历一组文本，逐条翻译
- **批量处理知识库结果**：遍历多条召回片段做摘要或分类
- **多维度评估**：对同一段内容，用不同专家 Prompt 评估（质量/合规/风格）
- **列表数据处理**：用户输入一个列表（如"提取以下 5 家公司的信息"），逐条搜索

**配置要点**：在循环节点中设置输入变量（如一个数组），循环体内的节点可访问每次迭代的当前元素。注意设置循环最大次数，防止无限循环消耗 Token。

**⚠️ 注意**：循环会大幅增加 Token 消耗（5 条数据 = 5 次 LLM 调用）。务必评估成本、设置合理的最大迭代次数。

### 6.2 代码节点（Code）实战：数据清洗

代码节点可以运行 Python / JavaScript 代码，用于 LLM 节点不方便处理的逻辑。

✅ 代码节点的典型用途

- **数据格式转换**：JSON ↔ 文本、时间格式转换、合并多个变量
- **数值计算**：价格汇总、折扣计算、评分统计——LLM 做数学容易出错
- **数据校验**：检查用户输入是否符合指定格式，过滤非法内容
- **字符串处理**：截取、拼接、正则提取——代码节点比 LLM 节点便宜且精准

```
# 代码节点示例：格式化订单数据 def main(raw_data: str) -> dict:    import json    data = json.loads(raw_data)     # 计算总金额    total = sum(item["price"] * item["qty"] for item in data["items"])     # 生成格式化文本    items_str = "\n".join(        f"- {i['name']} × {i['qty']} = ¥{i['price'] * i['qty']}"        for i in data["items"]    )     return {        "formatted": f"订单号：{data['order_id']}\n\n{items_str}\n\n合计：¥{total}",        "total": total    }
```

**💡 经验法则**：能用确定性逻辑（代码）解决的问题，不要用概率逻辑（LLM）。代码节点免费（不消耗 Token），而且输出可控。

### 6.3 混合检索与 Rerank 在工作流中的应用

当工作流中包含"**知识库检索**"节点时（这是工作流里最常用的节点之一），你可以配置与第 4 课相同的检索优化：

🔍 工作流中知识库检索节点的优化配置

- **检索方式**：混合检索（Hybrid Search = BM25 关键词 + 向量语义），适合专业术语和精确查询
- **Rerank**：勾选启用，将粗召回的 Top 20 做精排，最终只取 Top 3-5 送给 LLM
- **条件过滤**：可通过 metadata 过滤文档（如只检索"2026年版"的 SOP 文档）

### 6.4 变量作用域与节点间传递

📋 工作流变量的 3 种来源

- **开始节点变量（全局）**：整个工作流都能用，通常是用户的输入字段
- **上游节点输出**：每个节点都有 output 变量，下游节点直接引用，如 `{node_3.output}`
- **用户对话变量**（Chatflow 专属）：在整个对话 session 中持久化，适合记忆用户偏好

**💡 调试技巧**：如果不确定节点的 output 字段名，直接看节点右下角的"输出变量"面板，点复制即可。

### 6.5 错误处理策略

生产环境工作流必须有错误处理，否则一个节点挂了，整个流程中断。

🛡️ 工作流错误处理方案

- **方案 A（Dify 原生）**：在关键节点的"错误处理"设置中配置"继续执行，忽略错误"或"跳转到指定节点"
- **方案 B（条件分支兜底）**：在每个关键步骤后用条件分支判断 output 是否有效，无效则走 fallback 分支（如"回复：系统繁忙，请稍后再试"）
- **方案 C（代码节点捕获）**：敏感操作放在代码节点的 try/except 里，统一返回错误格式
- **Token 超限处理**：在 LLM 节点设置最大 Token 和截断策略，防止上下文溢出

## 七、本节课重点回顾

- ✅ 工作流适合：需要判断分支、调用工具、多步骤处理的场景
- ✅ 核心节点：开始、LLM、条件分支、工具、模板、结束
- ✅ 搭建流程：创建工作流 → 配置开始变量 → 添加节点并连线 → 配置每个节点 → 测试
- ✅ 意图识别是工作流常见第一步：用 LLM 节点输出结构化标签
- ✅ 调试靠运行日志：每个节点的输入输出都可见
- ✅ 最佳实践：先画流程图、单节点单职责、设置默认分支、做错误处理
- ✅ 进阶技巧：代码节点处理逻辑、循环节点批量处理、错误处理兜底
