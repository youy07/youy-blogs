理解 Agent 与工作流的区别，在 Dify 里搭建一个能主动调用工具的智能体——"快递查询 Agent"。

## 一、Agent 是什么？与工作流有什么区别？

**工作流**是你画好流程图，AI 按图走；
**Agent**是你给 AI 一堆工具，AI 自己决定先做什么、再做什么。

#### ⚙️ 工作流（Workflow）

- 流程是**固定**的，你画好每个步骤
- 适合：步骤明确、可预期的任务
- 例：接收邮件 → 判断类型 → 回复模板
- 可控性强，但不够灵活

#### 🤖 智能体（Agent）

- 流程是**动态**的，AI 自主决定步骤
- 适合：步骤不确定、需要灵活判断的任务
- 例：用户问"帮我查快递+天气+写日报"
- 灵活性强，但可控性弱

**💡 选择建议**：步骤固定 → 工作流；步骤不确定 / 需要 AI 自主判断 → Agent。两者也可以结合使用（工作流里调用 Agent 节点）。

## 二、Agent 的工作原理（ReAct 模式）

Dify 的 Agent 基于 **ReAct**（Reasoning + Acting）模式，流程如下：

🔄 ReAct 循环

1. **Think（思考）**：AI 分析用户问题，决定第一步做什么
2. **Act（行动）**：调用一个工具（如查快递 API）
3. **Observe（观察）**：拿到工具返回的结果
4. **Think again**：根据结果决定下一步，或直接回答用户
5. 循环直到任务完成

**最大迭代次数**：在 Dify Agent 配置里可以设置（推荐 5-10 次），防止 Agent 无限循环消耗 Token。

## 四、实战：搭建"快递查询 Agent"

跟着步骤走，搭建一个能查快递的 Agent（使用免费的快递查询 API）：

**1** 

#### 创建工作流应用（Agent 模式）

工作台 → 创建应用 → 选择**"Chatflow"**（对话流）→ 填写名称（如"快递查询助手"）

注意：Dify 里 Agent 能力是在"Chatflow"或"Workflow"应用里通过添加"Agent 节点"实现的，不是独立的应用类型。

**2** 

#### 添加 Agent 节点

- 在画布上，把默认的"LLM"节点替换成**"Agent"**节点（左侧面板 → 搜索"Agent"）
- 从"开始"节点连线到 Agent 节点
- 从 Agent 节点连线到"结束"节点

**3** 

#### 配置 Agent 节点

- **模型**：选择你配置的模型（推荐 DeepSeek-V3 或带推理能力的模型）
- **提示词**：描述 Agent 的角色和能力（见下方示例）
- **最大迭代次数**：设为 5（防止无限循环）
- **工具**：点击"添加工具"，选择要启用的工具

\# Agent 提示词示例（填入 Agent 节点）

你是一个快递查询助手。

\## 能力
\- 当用户提供快递单号时，调用快递查询工具获取物流信息
\- 如果用户信息不足，先询问必要的参数
\- 用简洁清晰的语言向用户汇报查询结果

\## 要求
\- 每次只调用一个工具
\- 如果用户问题无关快递，礼貌地引导回快递查询场景

**4** 

#### 添加自定义工具（快递查询 API）

Dify 支持添加自定义 HTTP API 工具：

- 设置 → 工具 → 自定义工具 → 创建工具
- 工具名称：`快递查询`
- 描述：`根据用户提供的快递单号和快递公司，查询物流信息`（这个描述很重要，AI 靠它决定是否调用这个工具）
- API 地址：填入快递查询 API 地址（如 `https://www.kuaidi100.com/query`）
- 请求方法：GET 或 POST（根据 API 文档）
- 参数配置：定义 API 需要的参数（如 `nu` = 快递单号）

**⚠️ 没有快递 API？用这个免费方案**
在 Agent 工具里启用"联网搜索"工具，让 Agent 自己搜索快递单号（效果不如专用 API，但可以快速测试 Agent 效果）。

**5** 

#### 测试 Agent

预览 → 输入测试问题：

- "帮我查一下快递，单号是 SF1234567890"
- 观察 Agent 是否调用了正确的工具
- 查看运行日志，看 Think → Act → Observe 的完整过程

## 五、深入理解：自定义工具配置

自定义工具是 Agent 开发的核心能力——让 AI 调用你们公司的内部 API。

#### 📡 自定义工具配置示例（快递查询）

假设你们公司有一个内部快递查询接口

```
# API 信息 URL: https://api.your-company.com/express/query Method: POST Headers: {"Authorization": "Bearer {{ api_key }}"} # 请求参数（Dify 会自动生成工具描述，AI 据此填参数） Body: {  "tracking_no": "{{ tracking_no }}",  // 快递单号（必填）  "company": "{{ company }}"      // 快递公司（可选） } # 返回示例（Dify 会解析并让 AI 读取） {  "status": "在途",  "steps": [    { "time": "2026-06-13 08:00", "desc": "已揽收" },    { "time": "2026-06-13 14:00", "desc": "运输中" }  ] }
```

**💡 工具描述写作技巧**
工具描述是 AI 决定是否调用它的唯一依据，要写清楚：
① 这个工具能做什么 ② 需要什么参数 ③ 什么场景下用
例："根据用户提供的快递单号查询物流信息，需要参数：tracking_no（快递单号，必填）"

## 六、Agent 开发最佳实践

✅ 提示词设计

- **明确角色和能力边界**：告诉 Agent 它能做什么、不能做什么
- **描述每个工具的用途**：在工具描述里写清楚使用场景
- **设置兜底回复**：当用户问题超出能力范围时，如何回复
- **限制迭代次数**：最大 5-10 次，防止 Token 消耗失控

⚠️ 常见问题

- **Agent 不调用工具** → 工具描述不清晰，或提示词里没引导使用工具
- **Agent 调用错误工具** → 工具描述有歧义，多个工具描述太相似
- **Agent 无限循环** → 最大迭代次数没设限制，或工具返回格式有问题
- **Token 消耗过高** → 迭代次数太多，或工具返回数据太大

## 进阶：Function Calling 原理与多 Agent 协作

🔧 Function Calling（函数调用）是 Agent 调用工具的底层机制

理解 Function Calling 协议是调试 Agent 工具调用问题的关键。它不是 Dify 独有的概念，而是大模型 API 的标准协议。

### Function Calling 是怎么工作的？

当 Agent 决定调用工具时，底层发生的是：

1. **用户发消息**："帮我查快递 12345678"
2. **LLM 判断要调用工具**：不是直接回复文本，而是返回一个 `function_call` 结构 —— 包含工具名和参数 JSON
3. **Dify 执行工具**：Dify 收到 function_call → 运行对应的自定义工具 → 拿到返回结果
4. **把结果送回 LLM**：Dify 把工具返回的内容注入到对话上下文 → LLM 基于结果生成最终回复

```
// LLM 返回 function_call（实际不可见，了解原理即可） {  "id": "call_abc123",  "type": "function",  "function": {    "name": "tracking_query",    "arguments": "{\"tracking_no\": \"12345678\"}"  } }
```

**💡 关键理解**：Agent 的"智能"来自两个环节——
① LLM 理解用户意图，**正确选择工具并生成参数**（这步靠提示词和质量好的 LLM 模型）
② Dify/SDK 负责**执行工具调用并将结果返还 LLM**（这步靠正确的工具 API 设计和返回格式）

### ReAct 模式 vs Function Calling 模式

⚠️ 两种模式的关键区别

- **ReAct**：LLM 每次输出推理文本（"我需要查快递..."），Dify 从中解析工具调用。可观测性好，但 Token 消耗高（思考文字也计费）。**适合调试和演示**。
- **Function Calling**：LLM 原生输出 function_call JSON（不是文本），Dify 直接执行。速度快、Token 省，但不可见中间推理。**适合生产环境**。

大多数商用模型（DeepSeek、通义千问、GPT-4）都原生支持 Function Calling。在 Dify 的 Agent 节点中，模型类型选择后会自动适配，你不需要手动切换模式。

**⚠️ 调试要点**：如果 Agent 不调用工具或调用错误的工具，打开"运行日志"查看：
\- 有 function_call 但参数错 → 工具描述不清晰
\- 有 function_call 但工具没执行 → 工具 API 返回异常
\- 没有 function_call → LLM 判断不需要工具，检查提示词或工具描述是否匹配场景

### Agent 与知识库联动

Agent 节点可以直接关联知识库，让 Agent 在推理时自主决定是否检索知识库：

- **配置**：Agent 节点 → 上下文 → 添加知识库（和聊天助手应用的方式一样）
- **行为**：Agent 会判断什么时候需要查知识库（如用户问内部制度），什么时候用通用知识回答
- **效果**：比"LLM 节点 + 固定检索"更灵活——不是每个问题都检索，只在需要时才查

### 多 Agent 协作架构

当单个 Agent 难以处理复杂的多步骤任务时，可以用多个 Agent 分工协作。

✅ 三种常见协作模式

| 模式           | 方式                                 | 适用场景                                   |
| :------------- | :----------------------------------- | :----------------------------------------- |
| **串行流水线** | Agent A 输出 → Agent B 处理          | 先分析后执行（如先分类再回复）             |
| **监督者模式** | 监督 Agent → 判断 → 分派给专业 Agent | 客服路由（售后→售后Agent、产品→产品Agent） |
| **辩论模式**   | 多个 Agent 独立回答 → LLM 汇总判断   | 提高准确率（如法律咨询、医疗建议）         |

在 Dify 中实现多 Agent：在 Chatflow 工作流画布里**串联多个 Agent 节点**，用条件分支节点决定调用哪个 Agent。Agent A 的输出作为 Agent B 的输入上下文。

**💡 成本提醒**：每个 Agent 节点都会独立消耗 Token。串联 3 个 Agent 的成本约是 1 个 Agent 的 3 倍。对于 80% 的场景，单个 Agent + 多个专用工具就足够了，先别急着上多 Agent。

⚠️ 多 Agent 的代价

- **Token 成本翻倍**：每个 Agent 独立推理 + 工具调用
- **调试复杂度高**：出问题时要在多个 Agent 节点间定位
- **响应延迟增加**：每个 Agent 的推理都需要时间
- **提示词协同难**：多个 Agent 的提示词需要相互配合，修改一个可能影响全局

## 八、本节课重点回顾

- ✅ Agent = AI 自主决定步骤（vs 工作流 = 固定步骤）
- ✅ ReAct 模式：Think → Act → Observe → 循环
- ✅ 搭建 Agent：创建 Chatflow → 添加 Agent 节点 → 配置模型+提示词+工具
- ✅ Function Calling 是底层协议：LLM 返回 function_call JSON，Dify 负责执行
- ✅ Agent 可关联知识库，自主决定何时检索；多 Agent 串行协作适合复杂任务
- ✅ 设置最大迭代次数（5-10 次），防止失控
